# bazis-uploadable 2.9.0

Guests read the files of public objects: a public catalog shows the photos of its items
through the route of the files, without a token and without a link to the media host.
Nothing is declared: the rule follows the route sets that already serve guests, so
**upgrading makes files public** (see "What becomes public" before you upgrade).

## Features

- **Files of public objects.** A guest (no token) reads `GET /uploadable/file_upload/{id}/`
  and downloads `GET /uploadable/file_upload/{id}/download/` of a file if both hold:
  1. a route set that declares the field in `files_visible` serves its item to guests: a
     router of the application registers its `action_retrieve` and the dependencies
     FastAPI runs for it do not include `get_user_required` (checked on the registered
     route, not on `auth_required`; a route class no router registers does not count);
  2. the object that references the file is among the objects that route set shows a
     guest: its `restrict_queryset(qs, view, user=<the anonymous user of bazis-users>)`, all
     its objects if it does not override `restrict_queryset`.

  `included` of the public routes shows him those files too (`?include=photo`). Any
  other file is 404, the same answer as a file that does not exist.
- **`uploadable.W003`** (`bazis_doctor`): a route set that serves guests, declares
  `files_visible` and does not override `restrict_queryset` (nor declares
  `permit_public = True`, the convention of bazis-permit `permit.W002`, read by its name
  without depending on bazis-permit): the files of all its objects are public.
- `route_serves_anonymous(route_cls)`, `files_public_q(model)` and `anonymous_files()`
  (whether guests read some files, for a frontend contract beside `anonymous_uploads()`)
  in `bazis.contrib.uploadable.routes`; `files_visible_cache_clear()` also forgets which
  route sets serve guests.

## Changes

- The item and the download of `FileUploadRouteSet` are declared `public` (`x-bazis`,
  `security: [{}]` with bazis 2.21+) and take an anonymous user (`get_user_optional`):
  without a token they answer the files of public objects, 404 for any other file
  (before: 401). The list (`/`, `/_id/`), the schema routes and the upload (with
  anonymous uploads off) stay 401; update and delete stay 405.
- `restrict_queryset` of `FileUploadRouteSet` for an anonymous user (or none, without a
  user of the request): the files of public objects for `view`, none with `link=True`
  or for another action (before: none). It calls the `restrict_queryset` of the bases
  after it (bazis-permit) with the anonymous user, which narrow the public files as they
  narrow the files of a user.
- A route set whose `restrict_queryset` fails for the anonymous user (one that requires
  the user by a dependency of its own and filters by him) shows guests no file: a
  WARNING is logged and the files of the other route sets stay public. Only building its
  queryset is isolated, not the database query.
- The item of `FileUploadRouteSet` is public in every subclass: `cls_init` declares it
  over a `public` the subclass sets and keeps the dependencies it declares; a subclass
  keeps guests out with its `restrict_queryset`.
- The requests of guests to the item and the download are limited by
  `BAZIS_THROTTLE_PUBLIC` (default `30/minute`) per IP address and route
  (`AnonymousThrottle`); the users are not counted.
- The download keeps `Cache-Control: private, no-store` for the guests too.
- The sample project has a public catalog: `notes.Poster` (migration `notes.0003`) and
  `PosterRouteSet`, which shows a guest the published posters and declares `photo`.

## What becomes public

After the upgrade a guest reads the files of the fields of `files_visible` of every
registered route set whose item does not require a user, for the objects its
`restrict_queryset` returns for an anonymous user:

- a route set of `UserRouteBase` (bazis-users) or a plain `JsonapiRouteBase` with
  `files_visible` and its own `restrict_queryset`: the files of the objects it returns for
  the anonymous user;
- the same without `restrict_queryset` of its own: the files of **all** its objects
  (`uploadable.W003`);
- a route set of bazis-permit (`PermitRouteBase`): the files of the objects the roles for
  anonymous users let him view; none without such roles;
- a route set of `UserRequiredRouteBase` (or `AuthorRequiredRouteBase`), or whose item
  depends on `get_user_required` in a dependency of its own: nothing;
- a route set whose item requires the user by a dependency of its own that does not use
  `get_user_required`: it counts as serving guests, its `restrict_queryset` gets the
  anonymous user; if it fails for him, its files stay private and a WARNING is logged;
- a file no object references (an anonymous upload not attached, a generated file):
  nothing.

Run `python manage.py bazis_doctor` after the upgrade and before you deploy: a
`uploadable.W003` names a route set whose files all became public.

## Requirements

- Unchanged: bazis 2.16, bazis-author 2.4, bazis-users 2.9.

## Upgrading

- The package has no new migration.
- Review the list above. For a route set whose objects a guest should not read with
  their files: restrict its objects for an anonymous user in `restrict_queryset`
  (`qs.none()` if they are all private), or make it require a user
  (`UserRequiredRouteBase`). If all its objects and their files are public, declare
  `permit_public = True` to say so (`uploadable.W003` is then silent).
- A subclass of `FileUploadRouteSet` that overrides `restrict_queryset`:
  - if it returns `qs.none()` itself for `user is None` (or an anonymous user), guests
    keep reading no file through it: return `super().restrict_queryset(...)` for him to
    serve the files of public objects;
  - if it returns `super().restrict_queryset(...)` for `user is None` (the pattern of the
    guide, `own`), guests now read the files of public objects through it; it must not
    widen them for a guest (keep its own rule for the users only).
- A client that treated 401 of the item or the download as "log in" gets 404 for a
  guest now: ask for a login on the 401 of the list, or before the request.
- A page that shows many files to guests: raise `BAZIS_THROTTLE_PUBLIC` (a dynamic
  setting) or the guests get 429 `ERR_THROTTLED`.
- Tests that define or register a route set with `files_visible` after the application
  is loaded call `files_visible_cache_clear()`.

## Security notes

- The rule is taken from the registered routes: a route class becomes public for the
  files only when a router serves its item to guests, so a declaration on a route class
  no router registers, or on one that requires a user, opens nothing.
- A guest never lists the files and never links one: `restrict_queryset` is empty for
  him with `link=True` and for any action but `view`; a file he does not see is 404,
  the same answer as a file that does not exist (no existence is told).
- Residual risks:
  - The visibility follows the objects, not the field permissions: a field permission
    that hides the relation field of a public object does not hide its file (as for the
    users).
  - A route set whose item requires a user by another means than `get_user_required`
    (a dependency of its own that raises 401 without calling it) counts as serving
    guests: require the user with `get_user_required`, or give it a `restrict_queryset`
    that returns `qs.none()` when `not user.is_authenticated`. If its
    `restrict_queryset` fails for the anonymous user, its files stay private (a WARNING
    in the log), but `anonymous_files()` still counts it: the contract says that guests
    read files while that route set shows them none (a known difference).
  - Which route sets serve guests is resolved once the application is loaded (as the
    declarations of `files_visible`); a router registered later is seen after
    `files_visible_cache_clear()`.
